Lapisan Pemrosesan (per sinyal)

1Transport — kafka_worker

Consume acis-queue-signal-success, proses per-batch (serialize per object_id agar tak balapan), publish acis-queue-lifecycle, commit offset (at-least-once). Stateless.

2Lookup PG (read-only)

Dari object_id: ambil meta objek (acis_lc_objects), state terkini + riwayat (acis_lc_lifecycle), topik & query (acis_topic_management), brief/persona (acis_client), timing trial (acis_lc_trial_meta).

3Recompute Health (Elasticsearch)

Index unified acis-data-*. Retrieval EXACT lewat _metadata.object.id (anti-twin) dengan fallback ke lucene_query topik. Window waktu pakai crawling_at. Hasil: velocity, volume, recency, client_relevance → health_score.

4Decision Engine (§5b)

Precedence ruleset menentukan transisi state/mode. Dua mode terpisah lewat env: deterministic (rules) atau agent (LLM, + fallback otomatis ke deterministic). Setiap transisi dapat reasoning yang kebaca manusia.

5Publish — payload lifecycle

Payload acis-queue-lifecycle: current → transition_to (state/mode/health + breakdown velocity/volume/recency/client_relevance), inactive_reason (reasoning), lucene & semantic query. Engine downstream yang menulis riwayat ke DB.

Lifecycle Rules
State Machine & Health Score
Tiap objek punya state & mode. Health score (0–100) dihitung ulang tiap sinyal, lalu ruleset precedence §5b menentukan transisinya. Validator struktural (Opsi B) hanya menjaga konsistensi state↔mode.

State & Mode

TRIAL ACTIVE · HOT ACTIVE · COLD ACTIVE · ON_DEMAND INACTIVE · DORMANT INACTIVE · DECAYING RETIRED

Health Score

health_score = velocity·0.30 + volume·0.20 + client_relevance·0.30 + recency·0.20 (clamp 0–100) velocity tren post 24 jam-skrg vs 24 jam-sebelum # tanh saturasi volume jumlah post 7 hari # 1 − e^(−n/ref) recency seberapa baru post terakhir # 100·0.5^(jam/half-life) client_relevance relevansi post ke topik (LLM scorer) # avg rel_score valid

Precedence Keputusan (§5b)

// D = silence-age (hari sejak post terakhir) · H = health_score 1. current = RETIRED → STAY (terminal) 2. D ≥ 90 hari → RETIRED 3. D ≥ 30 hari → INACTIVE / DORMANT 4. current = TRIAL & umur ≥ trial_max_days → band by H: H ≥ 80 → ACTIVE/HOT · 40–80 → ACTIVE/COLD · <40 → INACTIVE/DECAYING 5. ada post (D < 30): INACTIVE & H ≥ 40 → ACTIVE/COLD (resurrect) H < 40 sustained 14 hari → INACTIVE/DECAYING COLD & H ≥ 80 → ACTIVE/HOT (promote) HOT & H < 75 → ACTIVE/COLD (demote, instan) else → STAY 6. else → STAY
Hysteresis 75–80 mencegah HOT↔COLD flapping. Demote instan (H sudah teragregasi window). Masuk DECAYING konservatif (sustained 14 hari), keluar/resurrect instan (H≥40). Aging (DORMANT/RETIRED) murni dari last_post_at ES.
Fitur
Kemampuan Engine
Apa saja yang dilakukan engine tiap menerima sinyal — dari penilaian health, keputusan transisi, sampai penjelasan yang bisa dibaca analis.
⚡
Recompute Health Real-time
elasticsearch · windowed

Tiap sinyal, health dihitung ulang dari aktivitas ES: velocity (24h), volume (7d), recency, dan relevansi LLM — bukan angka statis.

🎯
Retrieval per-Objek (anti-twin)
_metadata.object.id

Post difilter EXACT ke object_id yang meng-crawl-nya, jadi objek se-topik tak lagi "kembar". Fallback ke lucene topik bila belum ter-tag.

🔀
Dua Mode Keputusan
deterministic | agent

Transisi & resurrect bisa pakai ruleset deterministik atau LLM agent — diatur env terpisah. Mode agent otomatis fallback ke deterministic bila gagal/low-confidence.

💬
Reasoning Tiap Transisi
inactive_reason

Setiap keputusan disertai penjelasan bahasa manusia (LLM) — kenapa objek naik/turun — dikirim ke Kafka & di-log untuk audit analis.

🧬
Refinement Lucene by Agent
redis cache · TTL 24h

Opsional: agent menyusun lucene_query spesifik per objek dari topik+brief+persona, di-cache di Redis agar deterministik & hemat.

📊
Breakdown Health di Payload
velocity/volume/recency/rel

Payload membawa komponen pembentuk health (current & transition_to) — transparan, siap dipakai dashboard downstream.

🛡️
Validator Struktural (Opsi B)
state ↔ mode

Memastikan kombinasi state/mode valid (ACTIVE→HOT/COLD/ON_DEMAND, INACTIVE→DORMANT/DECAYING) tanpa membatasi transisi — §5b yang berkuasa.

♻️
Aging & Resurrect
last_post_at

Sepi 30 hari → DORMANT, 90 hari → RETIRED (via ES). Objek dorman yang ramai lagi (H≥40) otomatis bangkit ke ACTIVE/COLD.

🔒
Read-only & Degraded-safe
no DB write

Tak pernah menulis DB. ES/LLM error → fallback aman (engine tak gagal-total). Objek tak terdaftar → skip + commit.

Cara Pembangunan
Arsitektur & Pengembangan
Direfactor dari backend lama yang mencampur transport + orkestrasi + tulis DB, menjadi modul bersih yang meniru boilerplate contextual_intelligence/: transport tipis → satu orchestrator → agents/tools → db_clients.

Lapisan Kode (mirror boilerplate)

1

Transport — tools/kafka_worker.py

Worker tipis: consume → MainProcessor.process_signal → publish → commit. Serialize per object_id dalam batch, prefix-commit untuk at-least-once.

2

Orchestrator — main_processor.py

Satu pintu: parse sinyal → lookup PG → recompute health (ES) → decision §5b → reasoning → build payload. Testable tanpa Kafka.

3

Tools — rules · health · es_tool · lifecycle_repo · state_validator

Logika murni: ruleset §5b, formula health, agregasi ES (retrieval object_id/lucene), query PG read-only, validator struktural.

4

Agents — relevance_scorer · lifecycle_decision · lucene_refiner · transition_reasoner

Pembungkus LLM via eb_labs dengan provider factory (OpenAI / OpenRouter / vLLM). Hanya komponen ber-LLM yang jadi "agent".

5

Infra — db_clients · config · schemas

pg_client (asyncpg pool, read-only), es_client (HTTP, versi-agnostik), redis_client (cache), settings (env), payload Pydantic in/out.
