Layered Architecture

1 Extraction Layer — DocumentParser

Downloads the document from an S3/HTTP URL (or reads a local path) and converts it to Markdown via one of two methods: a local path (pymupdf4llm for PDF, python-docx for DOCX, tables preserved) or a remote Docling API with primary→fallback endpoints and OCR. Markdown is split by H1–H3 headings, falling back to page-break / recursive character splitting (~10k chars, 1k overlap), keeping each chunk's heading context. Multiple documents can be merged into one PDF or parsed in parallel.

2 Audit Layer — ChunkAuditorAgent

Each chunk is audited against four category-specific indicators. The agent is tool-using: it calls brave_search_single + fetch_url_content to verify statistical claims against official sources (BPS, Kemenkeu, DJPK), and a calculator toolkit for precise ratio math on budget thresholds. Chunks run in parallel batches of 20 for throughput.

3 Aggregation Layer — SummarizerAgent

Scores are computed deterministically from every chunk (weighted average) and then override the LLM output — the model only writes the qualitative narrative, never the number. For large documents it summarizes hierarchically: partial summaries per batch of 10 → recursive merge → one final summary, so token budgets stay bounded at any document size.

4 Reporting Layer — ReportGeneratorAgent

Turns the summary plus a lightweight per-section scores table into a structured Markdown report — executive summary, scorecard, per-indicator breakdown, completeness checklist, critical findings, and prioritized recommendations — strictly avoiding any internal "chunk" wording in favour of document section names.

5 Rendering Layer — InfographicGenerator

Prepends a strict design spec (locked CSS + mandatory section order) and POSTs the report to a rendering API (Claude Sonnet 4.5 via OpenRouter), then converts the result to an A4 PDF. Header/footer toggles between official Kemendagri letterhead (logo + Directorate General of Regional Financial Development) and neutral VERIDOCS branding.

Engineering Challenges Solved

1 Auditable, Not Hallucinated Scores

Government decisions need defensible numbers. The LLM only assigns per-indicator scores and writes prose; the pipeline recomputes the weighted total deterministically and overwrites whatever the model reported — identical inputs always yield the identical, explainable score.

2 Documents of Any Size

Inputs range from a 2-chunk draft to a 160-chunk merged budget book. A hierarchical map-reduce summarizer (partial → recursive merge → final) keeps every LLM call within its context window regardless of page count.

observed: 2 → 160 chunks/doc runtime: ~3 min → ~35 min end-to-end

3 Verifying Claims Against Reality

Anomaly detection can't rely on the model's memory. The auditor searches Brave for official statistics (BPS / Kemenkeu), scrapes the source page through a knowledge-repository proxy, and only then classifies a claim VALID / ANOMALI / UNVERIFIABLE — never inventing a ground truth.

4 Precise Budget Math

Threshold compliance hinges on exact ratios. Instead of trusting LLM arithmetic, the Perda auditor delegates every division/percentage to a deterministic calculator toolkit, so "education = 18.5% of APBD" is computed, not guessed.

5 Resilient Long-Running Jobs

A 35-minute audit can't block an HTTP request. Jobs are enqueued in Redis and run by an async worker pool (semaphore-bounded), with a resume_from_step3 path that re-runs summary→report→infographic from saved chunk audits without re-auditing.

6 Print-Safe Infographics

The render output must survive HTML→A4 PDF conversion on mobile and print. The design spec bans wide tables, fixed widths and media queries, mandates card-list layouts for findings, and ships a locked CSS block the renderer must copy verbatim.

Pipeline
How a Document Becomes a Scored Audit Report
Five orchestrated stages run inside MainProcessor.process(). Every stage writes a trace artifact (step1…step5 + final_result.json) so any run is fully reproducible and resumable.
1

Document Parsing

Download (or read locally) the main document plus optional supporting documents. Convert to Markdown, then split by headings into context-retaining chunks. Auto-detect the document title from the first chunk and persist step1_parsed_chunks.json.

pymupdf4llm / doclingheading splitmerge or parallel
2

Chunk Auditing

For each chunk, the ChunkAuditorAgent scores all four indicators, calling web-search/scrape and calculator tools as needed. Chunks process in parallel batches of 20; failures degrade gracefully into a safe error result so one bad chunk never sinks the run. Each chunk's weighted score is recomputed in code.

batch_size = 20tool-callinggraceful degradation
3

Summarization & Scoring

Deterministic weighted averages and anomaly counts are computed across all chunks. The qualitative summary is produced directly for small docs, or hierarchically (partial batches of 10 → recursive merge → final) for large ones — then the deterministic scores are stamped back over the LLM result.

map-reducedeterministic overrideSUMMARY_BATCH=10
4

Report Generation

The ReportGeneratorAgent assembles the final summary and a per-section scores table into a complete Markdown report following a mandated structure, ready to be visualized. A fallback report is emitted from raw scores if the LLM call fails.

structured markdownsection-namedfallback-safe
5

Infographic Rendering

The report is injected into a category-specific design prompt (with the chosen header/footer block) and rendered to an HTML infographic, then converted to a download-ready A4 PDF. Three retries with exponential backoff protect against transient render failures.

Integrations
External Services it Orchestrates
Beyond the LLM providers, the engine stitches together extraction, evidence, rendering, queueing and storage services into one audit flow.

1 Docling Extraction API

Optional server-side extraction with OCR, table-structure recovery and a primary→fallback endpoint pair. The manual pymupdf4llm path is the default; Docling handles scans and tricky layouts.

2 Brave Search + Knowledge Repo

Claim verification scrapes Brave search results through a proxy and fetches full page text via a knowledge-repository endpoint — turning "the document claims X" into a checkable VALID/ANOMALI verdict with a cited source.

3 Infographic Render API

A POST with the design spec returns an HTML s3url; a second download-a4 call converts it to a print-ready A4 PDF. Both wrapped in retry/backoff.

4 Redis Job Queue

Audits are enqueued under data_auditor_agent:process:*, picked up by an async worker loop with a 10-slot semaphore, moved through pending→processed, and reported back to an upstream gateway log.

5 S3 Object Storage

Source documents are pulled from S3/HTTP URLs and generated infographics/PDFs are served back from object storage — the dashboard and consumers only ever see URLs.

6 Trace Artifacts

Every run writes step1…step5 + final_result.json to a timestamped folder, enabling reproducibility, debugging, and the resume_from_step3 shortcut.
