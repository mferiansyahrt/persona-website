System Architecture
Position in the Adaptive Crawling System
Contextual Intelligence sits at the Topic Management layer of the ACIS pipeline. The Lifecycle Engine (upstream) decides which keywords/topics to crawl and at what cadence; the crawler harvests posts and publishes anchor signals; this engine then transforms each anchor into a coherent stream of events and issues.

Layered Architecture (5 Layers)

1 Input — Kafka Anchor Stream

Each input is exactly one post + a _metadata envelope (object id, client id, platform, lifecycle state from the upstream Lifecycle Engine, plus a query hint). The schema-discriminator routes the payload to either the socmed or news normalizer based on the platform field. Schema discrimination handles 12 platforms across 2 source types.

Kafka topic: anchor input (TBD) 12 platforms 2 schemas: socmed / news

2 Tahap A — Context Retrieval

Single post → enriched pool. Embeds the anchor (eBdesk 1024-dim), looks up top-K matching tag centroids in Qdrant (dual-node failover), then retrieves up to 20 related posts from Elasticsearch (read-only — both prod-social-media-2026* and prod-news-2026*). A semantic relevance guard filters out unrelated noise.

Qdrant kNN ES 81 multimatch cosine guard ≥ threshold TRY 2 fallback

3 Tahap B — Event/Issue Pipeline

EventExtractor LLM converts the post pool into structured events (label, narrative, entities, claims, location, sentiment). Events are cross-batch deduped (cosine), gate-checked (3 rules), and matched against existing issues via kNN. Each event becomes ATTACH (to an existing issue), WAIT, or FORM_NEW. New issues are labeled and classified by the ContextLabeler agent.

EventExtractor LLM cosine dedup 3-rule gate ES 51 kNN ATTACH / WAIT / FORM_NEW

4 Storage — Elasticsearch 51

Events and issues are persisted to dedicated indices. The acis_issues index uses native dense_vector + cosine kNN search on the issue centroid, making issue clustering scalable across millions of issues without an external vector store.

acis_events (per event) acis_issues (centroid + meta) native kNN search

5 Output — Kafka Result Stream

For each anchor message processed, the engine publishes a single result payload to acis-contextual-intelligence-result. The payload includes the formed/attached issues with their issue_type classification, dominant narrative, entity signature, and event linkages. Downstream consumers (analytics, dashboards) subscribe directly.

Kafka: acis-contextual-intelligence-result at-least-once delivery prefix-commit per partition

Pipeline Stages
From Anchor Post to Classified Issues
Two stages: Tahap A (Context Retrieval) takes one post and expands it into a pool of semantically related posts. Tahap B (Event/Issue Pipeline) turns that pool into structured events, then clusters them under umbrella issues.
Why retrieve more posts? A single anchor post is rarely enough to form a meaningful issue. To detect actual events (need ≥3 events from multiple platforms with shared entities), the engine first expands the context — finds posts about the same topic across both social media and news, within a 24-hour window.
1

Schema Discrimination & Anchor Normalization

The _metadata.platform field routes the raw Kafka payload to either the socmed or news normalizer. Each schema knows its own field layout — Twitter full_text, news title+content, etc. — and produces a unified UnifiedAnchor object. A unified date normalizer handles four input formats (Twitter, News ES, ISO8601, unix epoch).

SOCMED_PLATFORMS = 8NEWS_PLATFORMS = 44 date formats
2

Anchor Embedding

The anchor text (title + content) is embedded via the eBdesk API (1024-dim, L2-normalized). The same vector is reused later for relevance filtering — saving one API call per anchor.

eBdesk v1dim=1024L2 normalized
3

Tag Centroid Selection (Qdrant)

Instead of feeding 200+ raw media_tags to an LLM, the system pre-computes a centroid embedding per canonical tag: take 50 posts tagged with this canonical → embed batched → mean → L2 normalize. At runtime: cosine search of the anchor vector vs all centroids → top-2 best-matching tags. Centroids refresh daily at 02:00 WIB. Tag canonical merge (lowercase) handles case variants like CYCLOPS + cyclops → one canonical.

Qdrant dual-node380 centroidstop_k = 2failover try-right-then-left
4

Elasticsearch Retrieval (TRY 1 + Fallback)

Query both prod-social-media-2026* and prod-news-2026* with: multimatch on text fields (boosted), filter on the selected tag variants, 24-hour window. Returns up to 20 hits per index. If TRY 1 returns 0 hits, fallback TRY 2 drops the media_tags filter and re-queries with just multimatch — ensures retrieval never returns empty when the topic is fresh and lacks tag coverage.

ES 81 (10.12.1.80)multimatch + filter24h windowTRY 2 graceful fallback
5

Semantic Relevance Guard

Multimatch alone returns lexical hits, not semantic matches. The guard batched-embeds all retrieved posts, computes cosine vs the anchor vector, and keeps only posts ≥ threshold (default 0.40, tunable). One batched embedding call (not N individual calls) keeps latency low — eBdesk supports list-of-strings input natively.

batched embedcosine threshold tunableanchor de-dup
6

Build Pool

Final output of Tahap A: pool = [anchor] + relevant_retrieved, capped at 30 posts. This pool feeds Tahap B as the input batch.

anchor always includedMAX_POOL = 30
From posts to issues. The pool of posts is converted to structured events by an LLM. Events are then deduped, gate-checked (count, shared entities, platform diversity), and either ATTACHED to existing issues or used to FORM_NEW umbrella issues.
1

Event Extraction (LLM)

Pool is split into batches (size 6 default). Each batch goes to the EventExtractor agent — a JSON-mode LLM that distills posts into structured events: event_label, narrative_frame, entities, claims, location, sentiment, source_posts. The prompt explicitly distinguishes events from opinions (single-sentence reactions → skipped).

JSON modepydantic validatedbatch size = 6
2

Cross-Batch Dedup

Each event is embedded; cosine similarity ≥ 0.85 merges duplicates across batches. The merged event keeps source_posts from all contributing duplicates so downstream traceability is preserved.

cosine threshold = 0.85union source_posts
3

Gate Check (3 Rules)

An issue forms only when the event cluster meets all three rules:
count ≥ N (default 2-3) — enough events to constitute a topic
shared_entity ≥ 1 — at least one entity appears in ≥ 2 events
platforms ≥ 2 — multi-platform coverage (avoid single-source bias)

All thresholds are tunable via environment variables. The gate prevents "issue formation" from a single isolated post.

tunable per envdiagnose object returned
4

Similarity Search vs Existing Issues

Each event vector is queried against acis_issues in Elasticsearch (native dense_vector kNN, top-K=2, cosine similarity). The query is scoped to the same object_id and client_id — issues are tenant-isolated. Score determines the next action:

≥ 0.70 → ATTACH  ·  0.50-0.70 → WAIT  ·  < 0.50 / empty → FORM_NEW

ES native kNNtenant-scoped2 thresholds
5

Sub-Cluster Before FORM_NEW

If multiple events all FORM_NEW, they shouldn't all collapse into one issue. The system sub-clusters FORM_NEW events by cosine ≥ 0.65 — each cluster becomes one distinct new issue. This prevents over-merging diverse events into a single umbrella.

sub-cluster threshold = 0.65
6

Issue Labeling + Classification (LLM)

Per sub-cluster, the ContextLabeler agent generates: issue_type (issue/framing/narrative), issue_label (umbrella name), dominant_narrative (1-2 sentence framing), entity_signature (top entities). Label styling adapts to issue_type — actor-centered for "issue", agenda-setting for "framing", observational for "narrative".

3-way classificationadaptive promptingJSON mode + pydantic
7

Persist + Publish

New issues + their events are bulk-inserted to ES 51. ATTACH events update their target issue's last_event_at and centroid (rolling average). Final result (without internal Tahap A diagnostics) is published to the output Kafka topic.

bulk insertcentroid rolling avgstrip tahap_a_summary

Issue Type Classification

"issue"
A concrete event/problem being publicly discussed. Has real action / impact / conflict (strike, policy, legal case, disaster). Verifiable facts. Clear stakeholders.
Example label Mogok Kerja Karyawan Indomaret 2026
"framing"
An interpretation pattern / point-of-view deliberately constructed by media or actors to give meaning to a series of events. Value-laden, agenda-setting, narrative engineering.
Example label Framing Polri sebagai Pelindung NKRI
"narrative"
A general discourse / discussion circulating without a dominant concrete event. Public conversation, opinion, recurring old issues, topical chatter.
Example label Wacana Work-Life Balance Generasi Muda
LLM Agents
Two Specialized Agents
The engine uses only two LLM agents — kept minimal to control cost and latency. Both agents use JSON-mode output with strict pydantic validation; malformed responses are caught and logged without crashing the pipeline.

Dashboard & Features
What the System Exposes
Three entry points: a Kafka consumer (primary production path), a FastAPI service (on-demand testing + admin), and CLI tools (manual testing + maintenance).
⇄

Kafka-to-Kafka Worker

Main production pipeline. Each worker process pulls anchor messages from the input topic, processes up to 15 in parallel (async semaphore-bounded), publishes results to acis-contextual-intelligence-result. Multi-worker via N independent processes; broker distributes partitions via consumer_group.

⇨

On-Demand Endpoint

POST /on_demand — user provides keyword + platform. The system strict-searches ES for the most representative matching post, treats it as a synthetic anchor, and runs the full pipeline. Used for testing, debugging, and ad-hoc queries.

⏱

Built-in Cron Scheduler

APScheduler embedded in the FastAPI service. Refreshes all 380 tag centroids daily at 02:00 Asia/Jakarta. No separate OS-level crontab needed. Manual trigger available via POST /admin/refresh_centroid.

⚙

Health + Readiness Checks

GET /health reports Tahap A readiness — Qdrant collection count, ES connectivity, canonical map availability. Service refuses to start serving anchors if Qdrant centroids are empty (cold-start protection).

⚡

Async Parallel Processing

Per-worker concurrency capped at 15 (tunable). Per Kafka batch: poll up to 50 messages, run them through asyncio.gather, then commit only the contiguous-successful prefix per partition. Provides at-least-once delivery — failed messages re-poll on next iteration.

⛨

Dual-Node Qdrant Failover

Qdrant deployed across two nodes (10.12.1.110 + 192.168.180.129). Writes go to both nodes via ThreadPoolExecutor. Reads try right-then-left with automatic failover — single-node outages don't take the pipeline down.

⛁

Tunable Thresholds

All key thresholds — relevance cutoff, gate min_count, similarity ATTACH/WAIT, dedup, sub-cluster — exposed via environment variables. No code changes required to calibrate the pipeline per use case.

⚏

Manual Testing Tool

tools/manual_test_kafka.py — load a JSON fixture, run the full pipeline, optionally publish to Kafka. Includes --skip-kafka mode for offline iteration on prompts and thresholds.

Build & Deploy
How the System is Built
Two-component deployment + manual testing tooling. Built incrementally over 16 implementation steps, each independently verifiable.

Deployment Components

1 Kafka Consumer Worker

tools/kafka_worker.py
  • Long-running process, consumes anchor messages
  • Async parallel processing — 15 concurrent per worker (tunable)
  • At-least-once delivery, prefix-commit per partition
  • Run N processes for horizontal scaling (worker_id-distinguished)
  • State isolated per process (Qdrant + ES clients not shared)
  • Verify Tahap A readiness on boot — refuses to consume if Qdrant empty

2 FastAPI Service

services/swagger_service.py
  • On-demand endpoint for keyword-driven testing
  • APScheduler runs cron jobs in-process (no OS crontab needed)
  • Admin endpoints for manual trigger + scheduler status
  • Single long-running uvicorn process (or systemd-managed)
  • Default port 8089

Build Order (16 Steps)

1-3

Foundation

Unified date normalizer (4 input formats), anchor normalizer with schema discriminator (socmed/news), settings.py extended with 21+ new config keys. No external services needed yet.

4-5

External Service Wrappers

Qdrant dual-node client with ensure_collection() (idempotent), ThreadPoolExecutor for parallel writes, search_with_failover() try-right-then-left. ES 81 client extended with factory pattern matching existing ES 51 client.

6-7

Tag Centroid Pipeline (Cron Side)

Whitelist builder runs ES terms aggregation, cleans 12 noise tags (rapidapi/sniffing/browser/etc.), case-merges to canonical lowercase. Tag centroid builder orchestrates: per canonical → sample 50 posts → embed_batch (1 HTTP call) → mean → L2 normalize → upsert to both Qdrant nodes. Runs as a daily cron job.

8-10

Runtime Tahap A Components

TagSelector (Qdrant lookup + canonical expand), PostRetriever (ES query both indices + de-dup vs anchor + TRY 2 fallback), RelevanceGuard (batched embed + cosine filter). Each component is independently testable via smoke-test entry points.

11-12

Integration

MainProcessor extended with async process_anchor(kafka_message) that chains Tahap A → existing Tahap B. FastAPI service adds POST /process_anchor endpoint + APScheduler hooks.

13-15

Testing & Calibration

Pytest E2E suite (40 cases — functional + edge cases + integration). Standalone tool to calibrate eBdesk concurrency limit (verified safe at 20 parallel). Stress test harness for throughput measurement at varying RPS.

16

Deploy

Update .env with production credentials. Eager-build all 380 centroids (~2 minutes). Verify via probe-test. Start FastAPI service (systemd-managed). Setup Kafka worker process(es). APScheduler takes over centroid refresh automatically.
